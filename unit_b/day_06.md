- EQ1: When should designers follow platform conventions, and when is it appropriate to deviate?

### Activities

1. **Warm-Up: Convention Scavenger Hunt** (10 min) `[EQ1, U1, K1]`
   - On your phone, find 3 UI patterns that appear across multiple apps (e.g., bottom navigation, pull-to-refresh, swipe-to-delete)
   - For each: Write down what the pattern does and why you think multiple apps use it
   - Be ready to share one pattern you found

2. **Today's Learning Goals** (5 min) `[EQ1, EQ2, U1, U2, K1, K2, K3, S1, S2]`
   - Today's essential question: When should you follow conventions, and when can you break them?
   - This connects to *rendering intent*: Once you know what to fix (forming), conventions help you execute in ways users understand
   - Preview: We'll explore platform conventions, learn the difference between task flows and user flows, then you'll create paper prototypes

3. **Direct Instruction: Platform Conventions & When to Break Them** (25 min) `[EQ1, EQ2, U1, U2, K1, K2]`

   **Part A: Why conventions exist** (10 min)
   - **I do:** Conventions are learned expectations. When you see a hamburger menu, you expect navigation. When you pull down, you expect refresh.
   - Users don't read instructions—they rely on patterns they've learned elsewhere
   - Breaking a convention = forcing users to re-learn (cognitive cost)
   - Show examples from scavenger hunt: Why did these patterns spread?

   **Part B: iOS vs. Android—key differences** (10 min)
   - **I do:** Walk through major platform differences:
     - Navigation: iOS uses edge swipe + back buttons in nav bar; Android uses system back button
     - Tab bars: iOS bottom tabs; Android often uses bottom nav OR top tabs
     - Typography: San Francisco (iOS) vs. Roboto (Android)
     - Actions: iOS often uses action sheets; Android uses bottom sheets
   - Key insight: Native apps *feel* native when they follow their platform's conventions
   - Show side-by-side: Same app on iOS vs. Android (Spotify, Twitter, etc.)

   **Part C: When breaking conventions is justified** (5 min)
   - **We do:** Discuss examples—good breaks vs. bad breaks
     - Good: Snapchat's camera-first launch (broke convention, but served core purpose)
     - Bad: Non-standard confirmation dialogs that confuse users
   - Rule of thumb: Break conventions only when the benefit clearly outweighs the learning cost
   - Ask: For the feature you're adding, are you tempted to break any conventions? Why?

4. **Direct Instruction: Task Flows vs. User Flows** (10 min) `[K3]`
   - **I do:** Introduce the pancake analogy (Erika Harano):
     - **Task flow** = the ideal linear path, no branches
       - "Making a pancake": preheat → gather → mix → cook → flip → eat
       - Shows the *system's perspective*—what the design expects users to do
       - Use to identify the key screens that need to be designed
     - **User flow** = the real experience with decisions and branches
       - "Mimi, a parent of three, making pancakes": START → Do I have all ingredients? → Can I substitute? → [the task flow] → Make more pancakes? → END
       - Shows a *specific persona's perspective*—including decision points, errors, and alternate paths
       - Use to catch dead ends, gaps, and edge cases
   - Key insight: Task flows can be *embedded within* larger user flows
   - **You do:** For your B2 deliverable, you're creating two *task diagrams*—the existing app flow and a modified flow showing your new feature added. Use color or a visual separator to demarcate the new feature from the original

5. **Hands-On: Paper Prototyping Workshop** (30 min) `[S1, S2, K3]`

   **Demo: Paper prototyping technique** (10 min)
   - **I do:** Show how to create a paper prototype:
     - One screen per card/paper (index cards or 8.5x11 sheets)
     - Draw enough detail that someone can "tap" elements while you flip pages
     - Focus on structure and flow, not polish—paper is for thinking, not impressing
   - Demonstrate a quick 3-screen prototype for a simple task
   - Show what "just enough detail" looks like

   **Practice: Sketch your first screens** (15 min)
   - **You do:** Create paper screens showing your new feature integrated into the existing app
   - Start with 3-5 screens covering your new feature
   - Think about: What conventions from Part B apply to your platform?

   **Quick test in pairs** (5 min)
   - Partner up and test each other's paper prototypes
   - Tester: Point at elements; ask "what happens if I tap here?"
   - Designer: Flip to the next screen, narrate what happens
   - Note where testers get confused

6. **Work Session: B1 Completion, B2a, & B2 Start** (remaining ~100 min) `[EQ1, EQ2, U1, U2, S1, S2, K3]`

   **What you're working on (in order of priority):**
   1. **Finish B1** — Complete User Flow & Competitive Analysis if not done (due end of class, PDF to Learning Suite)
   2. **B2a Competitive Analysis Matrix** — Polish your competitive analysis matrix in Illustrator or Figma, following the format shown in class (due end of class, PDF to Learning Suite)
   3. **Start B2 Paper Prototype + User Task Diagram** — Begin paper prototyping your new feature and creating user task diagrams (due before Day 7)
      - Paper Prototype: Your new feature screens on paper (5-6 screens for main feature, 3-4 for side features)
      - User Task Diagrams: Two diagrams — existing app flow and modified flow with your new feature added. Use color or a visual separator to clearly demarcate the new feature from the original
      - At least 1 usability test with someone outside class (not a classmate) — this can happen after class

   **Instructor circulating for 1:1s:**
   - Is your B1 competitive analysis thorough? Do you have enough competitors?
   - Are your paper screens testable? (Enough detail to "tap through")
   - Does your new feature apply platform conventions appropriately?
   - Have you identified where to test your prototype?

   **Due end of class:**
   - B1 User Flow & Competitive Analysis (PDF to Learning Suite)
   - B2a Competitive Analysis Matrix (PDF to Learning Suite)

   **Due before Day 7:**
   - B2 Paper Prototype + User Task Diagram (PDF to Learning Suite)
   - Brief notes from your usability test
